# SpecMutate: Locked Decisions & Architectural Constraints (AGENTS.md)

This document is a critical reference summary of the architectural boundaries, design patterns, and locked decisions for SpecMutate. Maintain compliance with these rules throughout all iterations.

## 1. LLM Core
SpecMutate uses **Gemini 2.5 Flash** (`gemini-2.5-flash`) exclusively. Up to 10 API keys are supported via round-robin rotation in `src/llm.py` (`GOOGLE_API_KEY` and `GOOGLE_API_KEY_1` through `GOOGLE_API_KEY_9`). On encountering a 429 quota/resource exhaustion error, the wrapper rotates to the next key, waits 2 seconds, and retries. Cached calls are saved to `.llm_cache.json` to reduce expenses during pipeline execution.

## 2. Benchmark Definition
The benchmark is defined in `benchmark.json` and consists of exactly 15 tasks in a 5/5/5 distribution:
- **5 Underconstrained**: Plants a weak specification (e.g., checks only length), leaving it vulnerable to buggy implementations.
- **5 Overconstrained**: Plants a spec that is overly restrictive, rejecting valid behavior from correct implementations.
- **5 Correct**: Plants a complete and correct spec that accepts correct behavior and rejects buggy behaviors.

Schema fields include `task_id`, `name`, `label` (underconstrained/overconstrained/correct), `description`, `reference_implementation`, `buggy_implementations` (with keys `name` and `code`), `planted_spec`, `what_is_wrong`, `correct_spec`, `repair_action` (replacing the deprecated `mutation_operator_to_fix`), `coverage_signal`, and `signal3_valid`.

## 3. Mutation Engine & Localization
The mutation engine applies three operators directly to the specification's AST nodes to localize bad constraints:
- `FlipComparison`: Flips comparisons (e.g., `<` to `<=`, `==` to `!=`).
- `RemovePrecondition`: Removes preconditions such as `assume()` statements or strategy boundaries (`min_value`, `min_size`).
- `RemovePostcondition`: Removes `assert` statements.

We do NOT implement `AddPostcondition`.
Crucially, mutations are scored by **coverage delta** in the correct implementation, not by test pass count. The operator yielding the highest coverage delta (newly uncovered lines/branches in the correct implementation) points to the bad constraint.

## 4. Signal Analysis & Fusion
SpecMutate evaluates specifications through four weighted signals:
- **S1 (Completeness, weight = 0.35)**: Measures what fraction of incorrect implementations generated by Gemini are rejected by the spec.
- **S2 (Discrimination, weight = 0.35)**: Measures how well the spec distinguishes pairs of buggy and correct implementations (i.e. one passes and one fails).
- **S3 (CrossHair, weight = 0.20)**: Uses the `crosshair` tool to verify the correctness of the spec as contracts. Checked via a mandatory health-check gate.
- **S4 (Stability, weight = 0.10)**: Evaluates spec consistency across 3 generations at a temperature of 0.7 against correct and trivially wrong implementations.

Verdict classification uses weighted fusion (`underconstrained` if fusion score < 0.45, `correct` if fusion score > 0.65). If correct_impl fails the spec, it is deterministically classified as `overconstrained`. If the best mutation is `RemovePrecondition` with `coverage_delta > 0`, it is also `overconstrained`.

## 5. Differentiator vs SOTA
SpecMutate differs from VeriAct (arXiv:2604.00280). VeriAct mutates implementation outputs to check if a spec is weak but cannot identify the specific faulty constraint. SpecMutate mutates spec AST nodes directly and uses coverage delta to pinpoint the error, providing grounded context (bad AST node, coverage delta, concrete counterexample) to the LLM during CEGIS repair. VeriAct operates in Java/JML; SpecMutate operates in Python/Hypothesis.
We never cite CoverAssert (Hardware SystemVerilog domain) as a Python PBT precedent.
